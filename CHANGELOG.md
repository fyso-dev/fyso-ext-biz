# Changelog

Versions are the Git tags of this repository. Earlier releases are described in their tags and pull requests.

## Unreleased

- Fix: Teams and Departments disable workflow actions when the required grants are missing and explain read-only access. A failed permissions lookup asks the user to reload, and a failed workflow start has its own translated message. Teams workflow grants resolve legacy wildcards through the gateway matcher.
- Fix: setup locks record their owning process and recover immediately after it exits. Scheduled sync skips a held lock successfully. Atomic writes clean up their own abandoned temporary files older than a day.
- Known limitation: in legacy project mode, the framework panel still matches exact capabilities. Wildcard grants for workflows outside the three Teams workflows may require explicit grants for the panel to expose them.
- Fix: a panel action that failed with anything that is not a coded error was reported as `connection_failed` ("could not reach Fyso Business"). It is now `biz_http_error` (with the status) or `operation_failed`, with their own en/es texts; `connection_failed` stays for the network failures the client throws itself. The extension API (`api.cjs`) answers the same.
- Fix: the Setup tab is available when managed access is configured, including projects without an agent grant. While the overview loads, the panel keeps the selected tab and waits for the connection state before opening Setup automatically.
- Fix: publishing from the panel passes the framework's preview `inputs` fingerprint as `FYSO_DIST_EXPECT_INPUTS`. Exit 6, or legacy exit 3 with the `preview_stale:` marker, asks the panel to show a new preview. The check requires the matching framework release. Older frameworks without the fingerprint keep the previous publish behavior.
- Fix: publish preview reports `framework_update_required` only when the framework rejects a preview flag. An unreadable dry-run response is reported as `unexpected_response`.
- Fix: managed-teams hooks report Biz HTTP failures as `biz_http_error` with their status and use `managed_teams_failed` for uncategorized failures. Known errors retain their codes.
- Fix: the Setup panel offers **Authorize again** for the four recoverable sync pauses (expired grant, disconnected, Biz unreachable and unexpectedly empty response). The action stays hidden while the project is frozen. Setup errors, publish checks and notices use localized labels and descriptions.
- Fix: setup preview and disconnect return `busy` while another setup operation holds the lock. Concurrent writes to setup state and OAuth grants use separate temporary files, and apply checks that the grant still exists before recording the project as connected.
- Fix: the gateway refreshes its Biz access report after setup operations and after a resumed sync. The next Setup status shows the newly published version.
- Fix: applying or publishing the setup from the panel made the extension's login process unresponsive for the length of the `mise run dist:*` commands (they ran with `execFileSync` in the gateway thread, which also answers the framework's readiness probe and the panel's forward-auth). The framework's own wait after `dist:add` then failed with `Extension processes not ready: ext-biz-login` and the panel hung. The long operations (preview, apply, publish preview, publish, merge, sync) now run in a worker thread (`setup-offload.cjs`), so the gateway keeps answering. One change at a time is still the file lock of the setup (a second request is answered `busy`), failures cross the thread as plain redacted fields (`message`, `status`, `files`, `detail`), a worker that crashes or exits without an answer is a failure, and the environment is never posted in a message. `stderrTail` now also redacts the token of `Authorization: Bearer <token>`.
- Fix: a transient Bot Architect failure (`fetch failed` while the native server was busy) failed `mise run up` on the Biz Partner bot. The bot provisioning is retried (at most three tries, increasing and capped delay, idempotent); its own refusals (name belongs to another bot, ambiguous, no engine), an HTTP 4xx, Dagu not configured and a run that outlives its timeout are final.
- Fix: `ext-biz-login` (and `ext-biz-publication`) stayed down after process-compose terminated them under host load: they had no restart policy and the readiness probe used the 1s default timeout. They now use `restart: always` and the probe allows 10 seconds, like the framework's own services.
- Fix: the publish preview failed the framework's `machine_paths` check because a comment in `managed-setup.cjs` spelled out a temporary-folder path. Comments, regexes and tests no longer contain machine paths, and `tests/machine-paths.test.cjs` runs the framework's `check-paths.sh` pattern over every file of the repository (it runs in CI with `mise run test`).
- Fix: a sync whose credential Biz rejected (401/403) or could not renew was paused as `biz_unreachable`. That is now `reauthorize_required`; `biz_unreachable` is only for a failed call (network, timeout, 5xx), and the pause keeps what failed (`paused.detail`) for the log. Signing in again clears any pause (not a frozen project) and syncs.
- Fix: every pause reason is shown as a sentence (screen and notices), never as a code. The status line falls back to the newest of the applied and self-published version when Biz's report is unavailable, and a self-published version reads "published by this project" without needing the report's `admin` flag.
- Fix: a sync paused for `reauthorize_required` (the Biz `framework_access` credential expires after 8 hours) only said "Sync is paused (reauthorize_required)". The Setup tab now says "Your Fyso Biz connection expired. Authorize again to keep syncing." with an **Authorize again** button that starts the profile sign-in; the same appears when a setup action answers `reauthorize_required`. After the sign-in callback the new grant is kept, a pause for that reason is cleared and a sync runs. Raw codes are no longer shown.
- Fix: the Setup status showed the version recorded locally, so a version published from the CLI (`mise run dist:publish`) looked old. The status shows the version Biz reports (`bizVersion`), and a publisher (`repo: biz`) whose `.copier-answers.dist.yml` records the version Biz shows records it as `selfPublished` (status and sync), so the sync does not replace its files.
- Fix: recent notices repeated the same failure every 15 minutes with raw `mise` stderr and temporary paths. Consecutive identical notices are one row with a count (x9) and the latest time, machine paths are stored as `<tmp>` / `<path>`, the panel shows five rows (**Show all** for the rest) and clamps long text to two lines (**Show more**). Notices already stored are shown collapsed and redacted too.
- Fix: **Disconnect** appeared twice on the Setup tab; only the page header one remains (`POST /profile/setup/disconnect` stays available).
- Design: the Biz screens (Teams, Business, Work, Access, Setup, agent email) follow the framework panel: its type scale, card sections with the panel's padding, button variants, banner/pill status lines, skeleton loading and empty states, and a clean publish preview (totals, one expandable row per kind with added/modified/removed badges, check pills, recent notices as list rows). Behavior, routes and i18n keys are unchanged.
- Feature: preview before publishing. **Publish this project's setup** now opens the framework's `dist:publish --dry-run --json` (new route `POST /profile/setup/publish-preview`): versions, files, bots, extensions, MCP servers, secret names, recipients and checks, with **Confirm publication** / **Cancel**; no changes or a failed check offers no confirmation, a stale base offers **Update and merge**. `publish` now needs the preview's `version` and `digest` and answers 409 `preview_stale` when the project changed since (the panel shows the new preview). A framework without `--dry-run` answers `framework_update_required`.
- Fix: after a publish the Setup tab said "Setup v2 applied" and no notice was added. The version printed by `dist:publish` (or `dist:status`) is recorded as `version` and `selfPublished`, a `published` notice is added, and a publisher reads "Setup vN published by this project". The automatic republish does the same.
- Fix: a failed publish only said `Command failed: mise run -q dist:key`. Commands now capture stderr; notices and the panel include its last 300 characters (secrets redacted), and `dist:key` is retried once.

## v0.7.1

- Fix: `copier update` failed with "Update the framework before enabling Biz-managed access" when `biz_access_organization` was set. Copier renders the old version in a temporary directory without `framework/panel/*.json`, so the missing access API read as version 0. The validator now refuses a missing or too-low access API only when the host's `extension-api.json` is present (a real host); the replay is tolerated.
- Fix: with Biz-managed access configured but no profile session, the Biz screen hid the Access and Setup tabs, so a project that never connected had no way to reach Connect. The Setup tab now shows whenever managed access is configured (`GET /api/ext/biz/profile/status` answers 200 only then), with a **Connect Fyso Biz** action that starts the profile login and explains the steps (sign in, consent, preview and warning before anything changes). An old grant (`reauthorize_required`) shows the same action. The Access tab appears once connected; without managed access nothing changes.
- Fix: the sign-in page CSP was `form-action 'self'`, and Chrome applies it to the form's redirect chain, so the 303 to Biz was blocked and the person stayed on the page. It now allows the validated Biz origin (`form-action 'self' <Biz origin>`, never a wildcard).

## v0.7.0

- Biz-managed setup: the organization's framework setup, published to Biz by an administrator as a distribution, reaches every member. New **Setup** tab: connect (profile login `framework_access`, age key registered with Biz, `dist:plan` plus the policy removals shown as a warning, snapshot, confirm), cancel (disconnect, nothing changed), disconnect and, for administrators, publish (`dist:publish`).
- "Compatible" mode removes only what the policy forbids: extensions and MCP servers outside the setup and the catalog (`framework:extensions:*`, `framework:mcp_servers:*`), own bots without `framework:bots:create`, and the teams of departments the person no longer holds.
- New workflow `ext-biz-sync` (every 15 minutes, `mise run biz:setup:sync`): same etag does nothing; a change is applied after a snapshot and announced in the panel. Administrators publish again when recipients are pending or changed. A failed, unexpectedly empty or `reauthorize_required` answer pauses the sync and removes nothing.
- `frozen: true` after a setup was delivered: read-only (as `cuidado`) in the panel policy and the MCP policy, sync stops, the secrets the distribution delivered are removed from `secrets.enc.yaml`. `frozen` on a project that never received a setup is shown as "no access yet" and changes nothing. Unfrozen when Biz answers `frozen: false`.
- The MCP policy now enforces the policy: a `cuidado` or frozen person may only call read tools.
- The mise environment sets `FYSO_DIST_BIZ_URL`, `FYSO_DIST_BIZ_ORGANIZATION` and `FYSO_DIST_BIZ_TOKEN_CMD` (`profile-token.cjs`) for the framework's Biz transport. Requires agentic-framework with the Biz transport (PR #131) and a Biz with the managed-setup endpoints (fyso-business ADR 0134).
- Fix: the managed-teams reauthorize guard now reads the access report with the profile token (it sent the agent grant), and a failed read blocks the destructive steps (unflagging, re-recording departments) instead of allowing them.
- Found by the end-to-end test against a fake Biz: the publisher registers its own age key before its first publish (a first publish with secrets failed), a project that never started snapshots by committing only, unfreezing installs the setup again so the removed secrets return, a second freeze does not leave an already removed secret pending, and a sync that installed nothing no longer reports replaced files.

## v0.6.0

- Access by department: `biz_access_project` is optional. `biz_access_organization` alone enables managed access (panel and MCP policy, template slots, feedback, managed-teams delivery); `project` is sent to Biz only when set. Installs that still set it work unchanged.
- `GET /oauth/framework-access` is read for the new optional `admin`, `departments` and `policy`; a Biz without them behaves as before. `GET /api/panel-access` returns them too.
- Managed teams come from `departamentos_framework` when no project is set; with `biz_access_project` set the legacy `proyectos_framework` path is kept unchanged.
- `reauthorize_required` from Biz (old OAuth grants) is no longer read as having no departments: the **Your departments** tab asks to reconnect Fyso Biz and the managed-teams delivery skips without changing anything.
- New panel tab **Your departments**: the person's departments with role, and their framework-freedom level.
- With a policy present, MCP server management also requires `framework:mcp_servers:catalog`.
- Template slot file names now depend on `biz_access_organization`.

## v0.5.2

- People sync without managed access: the new optional answer `biz_people_project` (a Fyso Biz project UUID, env `FYSO_BIZ_PEOPLE_PROJECT`) syncs that project's people over the project's own Biz connection. It does not enable Biz-managed access, does not need the framework access API and does not change the panel login: `panel-access.caddy`, `authorize.caddy`, `mcp-authorize` and the Workflows and feedback pages remain tied to `biz_access_project`.
- `biz_people_project` defaults to `biz_access_project`, so managed installs keep syncing unchanged; with it empty, `FYSO_BIZ_ACCESS_PROJECT` is still used.
- Without `biz_access_organization`, the organization that scopes the person ids is read from Biz (`proyectos_framework` → `organizacion`). Ids are derived exactly as in v0.5.0, so pages already synced are kept. Without a valid organization the run fails closed with `organization_unavailable`.
- The `ext-biz-people-sync` workflow, the `biz:people-sync` task, the connection-hook run and `people_synced`/`people_count`/`people_sync` in `GET /api/ext/biz/status` now follow the people project instead of managed access. Managed-teams delivery still requires managed access.

## v0.5.1

- Managed access: answering a human request from the panel (`POST /api/dagu/dag-runs/<workflow>/<run>/human-tasks/…/complete`, `…/push-back`, `…/resume`) now requires `workflow:<workflow>:run`; it was always refused before.
- Managed access: Dagu's wiki (`/api/dagu/wiki`, `/api/dagu/wiki/page`), used by the human-requests People directory, requires `action:wiki:read` to read and `action:wiki:write` to create, edit or delete; it was always refused before.

## v0.5.0

- People of the Biz project: with Biz-managed access, the people Fyso Biz assigns to the project (`listar_personas_proyecto`) are mirrored into the human-requests people directory as Dagu wiki pages `fyso-people/<uuid>` marked `"source":"biz"`, with a stable UUID per organization and Biz user. Missing people are created, renamed people updated and people Biz no longer lists removed; people added by hand are never touched, and a failed Biz or wiki read changes nothing.
- The sync runs from the connection hook, hourly through the new `ext-biz-people-sync` workflow and on demand with `mise run biz:people-sync` (both installed only with managed access).
- `GET /api/ext/biz/status` reports `people_synced`, `people_count` and `people_sync` with managed access.
- Requires a Fyso Business that offers `listar_personas_proyecto`, and fyso-ext-human-requests v0.2.0 or later to show synced people read-only.
